# SLICING-001: supplied FlashPrint and Prusa start/end comparison

## Scope and status

Offline inspection only. No file was changed, uploaded, started or replayed on hardware during this analysis. **This is not a corrected profile or a print-ready G-code replacement.**

User inputs, retained privately under ignored `upload/`:

- `test1.gx`: known-working FlashPrint output, generated by `ffslicer 1.30.0` according to its comments. This is the slicing-engine version, not necessarily the FlashPrint application version.
- `2026 - tungsten - holder.stl`: user identifies this as the source model for the GX.
- `m6x1x15.gcode`: problematic output, generated by PrusaSlicer **2.9.7** according to its header. Its trailing configuration is available for inspection.

These are **different models** in the FlashPrint and Prusa examples. Their toolpaths, final E positions and heights are not expected to be identical. Comparing their start/body/end contracts is still useful. Neither raw models nor full toolpaths are committed.

User-requested settings: 220 °C, 0.18 mm layers, approximately 0.27 mm first layer. The user initially described collisions, then noted that the end symptom may instead have been excessive extrusion; the file strongly supports that interpretation. It does not rule out other motion issues.

Line numbers below refer to decoded G-code lines (GX starts at its declared byte offset), or ordinary lines in the Prusa file, as inspected. Regenerating either file will change these references.

## Confirmed: absolute-E discontinuity at the end

Prusa's embedded config declares `use_relative_e_distances = 0`, with extrusion axis `E`. There is no `G92`/E-coordinate reset between the model and custom end code.

| Location | Existing command | E value |
| --- | --- | --- |
| Prusa line 28733 | Last model extrusion | 417.17445 |
| Prusa line 28734 | `G1 E415.17445 F2400` | 415.17445, a 2 mm retract |
| Prusa line 28739 | `G1 E778.4812 F1800` | 778.4812 |

Under the declared absolute-E intent, the last command requests **+363.30675 mm of filament**, not a retract. It is an E-only move **before** the custom Z lift (line 28740) and XY park (28741). Extruding a large blob at the last model position is therefore a strong explanation for the reported end symptom. Actual firmware mode/observed motion is not independently instrumented here.

The FlashPrint reference instead ends with E=619.2393 (line 137462), then E=616.7393 (137466): **−2.5 mm**, a small retract. Copying that job's final absolute E value into another job would not preserve this delta.

The Prusa footer itself contains the literal `E778.4812` in `end_gcode`. The user subsequently confirmed manually pasting that exact exit block into the Prusa profile. It is not an expression computed from the current print. This is a profile/template problem, not a GX-thumbnail or upload-CRC problem. The existing generated file retains it even after the profile is edited; it must be regenerated once a reviewed replacement is ready.

## Confirmed: startup prime/body E reference does not agree

Prusa custom startup ends its prime at E=17.4017 (line 42). After `G21`, `G90`, `M127` and comments, the first body retract is `G1 E-2 F2400` (51), then `G1 E.00001 F2400` (54). There is **no E reset** between them.

In absolute-E terms, the first change is **−19.4017 mm**, not −2 mm. The following change is +2.00001 mm. This demonstrates that the custom prime's E coordinate and the slicer's generated-body E origin are not harmonized.

The user also confirmed the pasted startup block ending in `E17.4017`. A future profile needs an explicit interface between custom prime and generated body: establish the expected E origin/mode without moving the extruder, or consistently adjust the body. A targeted candidate for **this absolute-E profile** is `G92 E0` after the last prime and before generated body code; the working FlashPrint file already uses that command elsewhere. It makes the next `E-2` a 2 mm retract instead of 19.4017 mm. This is an isolated state-contract correction, **not a complete hardware-validated start script**. Choose one owner for retractions: Prusa has already retracted 2 mm before custom end, so an additional generic retract could also double-retract.

## Other measured differences and risks

| Item | FlashPrint/reference or requested | Supplied Prusa file |
| --- | --- | --- |
| Temperature | 220 °C | 220 °C (matches) |
| Layer height | Comment: 0.18 mm | Config: 0.15 mm |
| First model layer | Actual reference `Z.280`; user requests about 0.27 | Actual/config: 0.35 mm |
| Prime height | 0.20 mm | 0.20 mm; this is not the first model layer |
| Nominal device dimensions | Captured `M115`: 140 × 140 × 140 | Bed corners ±75 (150 × 150), max height 160 |
| Z travel command | Reference uses `F420` (7 mm/s) | `G1 Z.35 F7800` at line 52, later same Z feed requests (130 mm/s) |
| Prusa speed settings | Not a Prusa reference profile | `travel_speed=130`, `travel_speed_z=0`, configured Z max feedrate 12; limits usage `time_estimate_only` |
| Last model/body Z | Reference: 50.000 (line 135980) | 18.95 (28627) |
| Custom end Z / park | Reference: 50.100 / X50.78 Y5.95, job-specific | Literal 30.100 / X69.05 Y−17.75 |
| Layer count | Reference comment: 277 | 125 `LAYER_CHANGE` markers, but custom start advertises 166 |
| Custom M118 Z | Reference: 50.10 | Literal 30.10, not the actual 18.95 model top |

The requested 0.27 mm first layer and reference's actual 0.280 mm must be reconciled with the export settings; do not assume a particular rounding/offset explanation without evidence. The Prusa file's 0.35 mm is clearly a different setting.

A separate, nonzero Z-travel setting and reviewed printer limits are needed. The requested feed rate is not proof of achieved speed: acceleration and firmware limits may cap it. Conversely, `time_estimate_only` is not proof that those limits were sent to/enforced by the printer.

The literal custom Z=30.100 **raises** logical Z from 18.95 in this particular Prusa example; it does not itself prove a downward plunge into that model. It would be unsuitable as a universal end height for taller models. Likewise X=69.05 is close to a nominal ±70 edge, but this file alone does not prove a physical border collision. Printer offsets, homing paths, clearances and nozzle geometry still require validation. Raw commanded G0/G1 XY extrema in this sample remain within ±70; the oversized profile remains a risk for future placements, not evidence that this particular file commanded X/Y=75.

The shared initial sequence includes `G90`, `G28`, `M132`, `G161`, `M6 T0`, `M651`, `M907` and `M108`. The shutdowns share `G162 Z`, `G28 X Y`, `M132`, `M652`, `G91`, `M18`. **Do not remove homing or M6 just because their semantics differ from a generic Marlin profile:** they also occur in the working file. Prusa additionally emits commands such as `M127`/`M73`; their Finder behavior has not been established by this comparison.

## STL/container observations

The supplied binary STL has 16994 triangles and a consistent binary length. Raw bounds are X=[−50,50], Y=[−25,5], Z=[−8,42], spanning 100 × 30 × 50 coordinate units. STL itself has no unit declaration; a millimetre interpretation is consistent with the user's model and the GX's approximately 50 mm print height. Translation/placement is not embedded as a printer profile in the STL.

The GX declares `(0,58,14512,14512)` as its four little-endian 32-bit values at byte 12. Its preview at byte 58 is a 14454-byte, 80×60, 24-bit BMP; G-code begins at byte 14512. This establishes a useful container baseline, not motion compatibility or all metadata semantics.

## Next implementation, before any generated hardware print

1. Recover the Prusa configuration as a private reference; use the existing 2.9.7 installation/CLI rather than writing a slicer engine.
2. Make a dedicated Finder profile with verified origin, nominal envelope and explicit Z speed; align the requested layer/temperature settings. Do not infer physical clearance solely from nominal build size.
3. Replace copied job-specific E/Z/XY/extents/layer-count constants with state-aware templates/adaptation. Define extrusion mode/origin at the prime/body boundary and exactly which component owns final retraction.
4. Define a bounded, model-height-aware clearance/park strategy consistent with the known Finder sequence. Do not blindly adopt generic `M82`/`M83` or a fixed Z-lift at the top of the machine's range.
5. Compare output offline, including these transition deltas and motion bounds. The mock checks protocol, not collision safety. Use a paired small STL/FlashPrint reference when available to isolate geometry/settings differences; the large reference is already sufficient to diagnose the E-state errors above.
6. Only after those checks: GX metadata/preview generation, dummy upload, then an explicitly approved supervised hardware trial. No unsafe/"fixed" file is generated by this report.

Prusa supports custom-code variables such as `max_layer_z` and `total_layer_count`, which may help remove literals; exact availability/syntax must be checked in the actual installed version. Reference: [Prusa placeholder documentation](https://help.prusa3d.com/article/list-of-placeholders_205643). Macro support does not itself validate Finder firmware semantics.
