## Observed GX offsets (zero-based byte offsets)

| Location | Bytes / interpretation |
| --- | --- |
| 0..11 | `xgcode 1.0\n\0` signature |
| 12..15 | little-endian uint32 value0; semantics not established |
| 16..19 | little-endian uint32 value58, the observed BMP start |
| 20..23 | little-endian uint32 value14512, observed G-code start |
| 24..27 | little-endian uint32 also14512; separate field's semantics unknown |
| 28..57 | other metadata; not decoded or synthesized here |
| 58..14511 | standalone BMP, 14454 bytes |
| 14512 onward | textual printer G-code |

Do not copy the remaining metadata from one print to another or assume the two
14512 fields always have the same meaning. No GX generator is implemented by
this finding and no plain G-code printability claim is implied.

## BMP header and pixels

The embedded data begins `BM` and follows the ordinary Windows BMP layout:

- 14-byte BITMAPFILEHEADER: file size14454, reserved fields0, pixel offset54.
- 40-byte BITMAPINFOHEADER: width80, **positive height60**, planes1, depth24,
  compression0 (`BI_RGB`), pixel-array length14400, no palette.
- X/Y resolution3780 pixels/metre; this is image metadata, not model dimensions.
- Pixels are **B, G, R** bytes, 8 bits per channel, with **no alpha**.
- Positive BMP height means bottom row first. For display with row0 at the top,
  reverse row order and swap B/R; do not reverse pixels inside each row.
- Row stride is `((width * 3 + 3) // 4) * 4`; here240 bytes, so no row padding.
  Other widths may need 0..3 padding bytes per stored row.
- Total size is `14 + 40 + 60 * 240 = 14454`. No JPEG, PNG, Base64, pixel RLE or
  custom image compression is involved in this sample.

## Read-only tool

```sh
mkdir -p .tmp/gx-preview
python3 tools/extract_gx_preview.py upload/test1.gx
# New paths only; existing files are never overwritten:
python3 tools/extract_gx_preview.py upload/test1.gx --output .tmp/gx-preview/new.bmp
python3 tools/extract_gx_preview.py upload/test1.gx --output .tmp/gx-preview/new.ppm
```

Without `--output` the tool prints metadata only. `.bmp` preserves embedded
bytes exactly; `.ppm` is a derived top-down RGB P6 file. It reads bounded input,
checks offsets/header/pixel sizes and supports only the reviewed uncompressed
24-bit BITMAPINFOHEADER layout (including standard negative/top-down heights).
It rejects unsupported compression/formats instead of guessing. It does not
rewrite GX or printer code, run the printer/slicer, create a thumbnail from STL,
or validate other header fields. Keep output images private unless reviewed.

Tests generate synthetic colored pixels to verify BGR conversion, bottom-up /
top-down rows, padding, invalid bounds/compression and overwrite refusal:
`python3 -m unittest discover -s tests -v`.

## Original next-work criteria (now addressed experimentally)

The separate implementation/evidence in GX_GENERATION.md follows these criteria.
Physical firmware/display acceptance and broader format validation still remain.


To generate previews for independent STL slicing, rendering and container
construction are separate stages: render the model with a known projection,
encode BMP, then build a GX header whose remaining fields are independently
understood. Compare multiple known-working GX samples with different images,
model sizes and print metadata before asserting a complete format. A thumbnail
can help identify a file but cannot make unsafe G-code or unsupported firmware
commands safe.
